결론

이식은 가능합니다. 다만 어떤 조직으로 옮기느냐에 따라 작업의 성격이 달라집니다. 소프트웨어를 만드는 조직이라면 기존 체계를 고쳐 쓰는 것으로 충분하고, 문서와 캠페인을 납품하는 조직이라면 운영 기반만 가져와 공정을 새로 짜야 합니다.

구성 요소별 게임 용어 포함 줄 비율

줄 비율은 용어가 얼마나 퍼져 있는지를 보여 줄 뿐이며, 동작이 얼마나 묶여 있는지를 보여 주지는 않습니다. 예를 들어 스킬은 15.2%에 불과하지만 엔진 전문가 라우팅이나 GDD 섹션 이름처럼 동작을 바꾸는 결합이 곳곳에 있습니다. 그래서 판정은 파일을 직접 읽고 내렸습니다. 엔진 레퍼런스는 내용 전체가 엔진 전용이므로 비율과 관계없이 교체 대상이어서 그래프에서 제외했습니다.

이미 설계된 전환 지점: project.kind

effects-map.md에는 game | tool | engine | mod | library 값을 받는 project.kind 키가 정의되어 있습니다. 원저자가 게임 이외의 프로젝트를 염두에 두었다는 근거입니다. 그러나 이 키는 "RESERVED, NOT IMPLEMENTED"로 표시되어 있고 읽는 스킬이나 훅이 하나도 없습니다. 실제로 쓰려면 detect-gaps.sh와 session-start.sh의 분기, yaml-helper.sh의 code root 결정, workflow-catalog.yaml의 종류별 단계 목록을 새로 만들어야 합니다.

대상별 적합도

아래 그래프는 구성 요소를 네 가지 판정으로 나눈 결과입니다. T1은 '유지'와 '수정'이 대부분을 차지하고, T2는 '제거'와 '재설계'가 절반을 넘습니다.

대상 후보별 적합도

직접 판정한 대상은 T1과 T2 두 가지입니다. 나머지 후보는 두 결과에서 추정한 값이므로 '추정'으로 표시했습니다.

전환 전략

먼저 확인할 질문: CCGS를 옮길 필요가 있는가

목적이 역할별 조언을 받는 것이라면 이미 설치된 도구로 충분할 수 있습니다. 이 환경에는 SuperClaude 페르소나(architect, frontend, backend, security, qa 등)와 engineering·design·finance 역할 플러그인이 설치되어 있습니다. CCGS를 옮길 이유가 되는 것은 단계별 산출물, 디렉터 게이트, 요구사항 추적(TR-ID), 스토리 증거 규칙, 세션 상태 보존처럼 프로젝트의 수명 주기를 관리하는 장치입니다. 이 장치가 필요할 때 전환이 의미가 있습니다.

A

포크 후 전면 전환

저장소를 포크하고 용어, 경로, 에이전트를 대상 도메인에 맞게 바꿉니다.

  • 결과물이 하나의 일관된 체계가 됩니다.
  • 재사용률이 높은 T1에서 가장 적은 작업으로 끝납니다.
  • upstream의 권장 병합 방식(UPGRADING.md 전략 A)을 사실상 쓸 수 없습니다. 파일 이름이 바뀌면 git의 유사도 기반 병합이 깨집니다.
  • CONTRIBUTING.md는 방향이 맞지 않는 PR을 닫는다고 명시하므로, 도메인 전환은 upstream에 되돌려 보낼 수 없습니다.

적합한 대상: T1

B

코어와 도메인 팩 분리

project.kind를 실제로 구현해 게임 팩은 그대로 두고 새 도메인 팩을 나란히 추가합니다.

  • upstream 파일을 가장 적게 건드리므로 병합 부담이 가장 작습니다.
  • 여러 도메인을 한 체계에서 운영할 수 있습니다.
  • 초기 공사가 가장 큽니다. project.kind 연결은 스위치를 켜는 일이 아니라 새로 만드는 일입니다.
  • 도메인마다 분기하는 스킬이 복잡해집니다.

적합한 대상: 게임과 다른 도메인을 함께 운영하는 조직

C

운영 기반만 선별 이식

새 저장소에 운영 기반(훅, 설정 해석기, 세션 상태, 게이트 장치, 스킬 테스트)과 범용 관리 스킬만 가져오고, 도메인 에이전트와 스킬은 CCGS의 골격을 본떠 새로 씁니다.

  • 게임용 잔재가 남지 않고 용어가 처음부터 깨끗합니다.
  • 에이전트 골격(협업 프로토콜 3종)과 팀 스킬 골격을 복사해 쓸 수 있습니다.
  • 가져오지 않은 기능(gate-check 기준, 추적성 체계 등)은 다시 만들어야 합니다.

적합한 대상: T2

권장안

T1이라면 A를 권합니다. 70% 이상을 살릴 수 있는데 C처럼 다시 쓰는 것은 낭비이고, B의 추가 공사는 게임 팩을 함께 쓸 계획이 없다면 얻는 것이 없습니다. 다만 운영 기반 파일(훅, yaml-helper.sh, 스크립트)은 최소한으로만 고치고 차이는 설정값으로 흡수해 두십시오. 그러면 나중에 upstream의 운영 기반 수정만 골라서(UPGRADING.md 전략 B, cherry-pick) 받아올 수 있습니다.

T2라면 C를 권합니다. 살릴 수 있는 것이 41.4%에 그치고 남는 부분이 대부분 운영 기반이므로, 게임 콘텐츠를 걷어내는 것보다 필요한 것만 가져오는 편이 작업량과 혼란이 모두 적습니다. 기능 단위의 전문 지식은 설치된 역할 플러그인에 맡기고, CCGS에서는 조율 장치만 가져오는 조합도 검토할 만합니다.

T1 권장 로드맵

포크 후 단계적 전환(전략 A)을 기준으로 한 순서입니다. 0단계부터 6단계까지가 최소 전환이며, 공정의 척추만 먼저 살려 실제 프로젝트에 쓰면서 나머지를 고치는 방식입니다.

  1. 범위와 용어 확정

    대상 조직, 기술 스택, 용어 대응표를 확정합니다. 이 결과는 이후 모든 일괄 치환의 기준이 됩니다.

  2. 게임 전용 요소 정리

    '제거' 판정을 받은 에이전트 5개, 팀 스킬 3개, 템플릿 5개, 규칙 4개와 엔진 레퍼런스를 지웁니다. 당장 전환하지 않을 스킬은 별도 폴더로 옮겨 호출되지 않게 합니다. 삭제한 뒤에는 이름이 다른 파일에 남아 있지 않은지 grep으로 확인합니다.

  3. 운영 기반의 게임 연결점 수정

    yaml-helper.sh의 열거값과 code root 표, detect-gaps.sh, validate-commit.sh, validate-assets.sh, pre-compact.sh, statusline.sh의 경로를 새 규칙에 맞춥니다. 아래 조용히 깨지는 지점 목록을 점검표로 사용합니다.

  4. 진입점 교체

    setup-engine을 setup-stack으로 바꾸고, start, help, workflow-catalog.yaml의 단계 이름과 산출물 경로를 새 공정에 맞춥니다.

  5. 공정의 척추 전환

    design/gdd/, game-concept.md, systems-index.md를 새 명칭으로 바꾸고, brainstorm, map-systems, design-system, design-review, gate-check처럼 '재설계' 판정을 받은 설계 단계 스킬을 다시 씁니다. story-done과 story-readiness는 CONTRACT.md를 함께 고칩니다.

  6. 에이전트 재편

    디렉터 3개와 리드의 도메인 지식을 제품 조직 기준으로 다시 쓰고, 엔진 전문가 15개를 선택한 스택에 맞는 3~5개로 교체합니다. 엔진 리드 에이전트의 tools: Agent(...) 허용 목록도 새 이름으로 바꿉니다.

  7. 검증

    /skill-test static all로 구조를 확인하고, 옛 경로와 용어가 0건인지 grep으로 확인합니다. 그다음 빈 샘플 프로젝트에서 /start부터 첫 스토리 종료까지 한 번 끝까지 실행합니다.

  8. 나머지 정리

    보류한 스킬, 템플릿, 디렉터 게이트, 문서(README, WORKFLOW-GUIDE 등)를 정리합니다. 필요하면 스킬 테스트 프레임워크의 행동 명세도 다시 씁니다.

작업량 추정

Claude가 초안을 쓰고 사람이 검토하는 방식을 가정한 시간입니다. 규모를 가늠하기 위한 값이므로, 실제 계획은 스킬 두세 개를 표본으로 전환해 본 뒤 다시 측정하는 것이 좋습니다.

환산 기준은 S 0.25~0.5시간, M 1~3시간, L 3~8시간입니다. T1 전체 전환에서 엔진 전문가 15개는 스택 전문가 4개를 새로 쓰는 것으로 계산했습니다. 1인이 주 30시간을 쓴다고 보면 T1 최소 전환은 약 3~8주, T1 전체 전환은 약 7~18주, T2는 약 8~23주입니다. 스킬 테스트 프레임워크의 행동 명세 123개를 다시 쓰려면 30~90시간이 더 듭니다.
