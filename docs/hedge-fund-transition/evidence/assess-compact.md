* gate-check is the single most cross-referenced skill in the entire 74-skill catalog (grep found it named by 34 other skill files, vs. the next-widest, sprint-plan, at 22). It must transplant early and be architecturally stable, since every hedge-fund domain skill written fresh will reference it from a 'next steps' section, exactly as it is referenced today.
* sprint-plan, sprint-status, settings, project-stage-detect, adopt and start form a second-tier 'spine' (each referenced by 4-6 other skills) that should transplant in the same wave as the operating foundation (hooks, yaml-helper.sh, session-state) the founder already scoped for Strategy C, because domain skills not yet written will assume their commands exist.
* Three components — bug-report, hotfix, tech-debt — score materially higher for a hedge fund than the mapping.txt T2 (knowledge-service agency) verdict suggests (T2 marks all three R = redesign/no-fit). The reason is structural, not cosmetic: a hedge fund, unlike a consulting/agency business, has a real, regulator-scrutinized code and model pipeline (OMS/EMS, risk engine, quant models), so game-studio bug-triage, incident-hotfix and tech-debt-register patterns are a closer structural match to a hedge fund than to an agency. day-one-patch and changelog show the same undervaluation for the same reason.
* gate-check's own mechanism — verdict precedence (FAIL > CONCERNS > NOT ASSESSED > PASS), the explicit 'a check that cannot report it did not run is not a check' discipline, and Chain-of-Verification challenge questions — is the single highest-value transplant candidate in this area for the review's stated regulatory requirements (independent CCO/CRO reporting lines, numeric-rule enforcement, audit trail). But it cannot be finalized as TAKE-MODIFY without a founder decision: today's director-panel width is *tier-scalable* (1 director at minimal workflow, up to 4 at full) via `.claude/skills/gate-check/SKILL.md:390-400`, and if a CRO/CCO seat is mapped onto that same scaling mechanism without change, compliance/risk review becomes skippable by a `modes.workflow` or `modes.review_mode` setting — which a regulated entity cannot allow.
* Cross-reference grep closes the transplant set for this area: within it, gate-check <- {milestone-review, retrospective, help, project-stage-detect, adopt, start}; sprint-plan <-> {sprint-status, scope-check, estimate, milestone-review, retrospective, help, tech-debt}; bug-report <-> {bug-triage, hotfix, day-one-patch}; changelog <-> patch-notes <-> {hotfix, day-one-patch}. ## findings
* DELIVERABLE 1 SUMMARY -- workflow-catalog.yaml (.claude/docs/workflow-catalog.yaml:1-427): schema is `phases:` -> dict of phase-id -> {label, description, next_phase, steps:[{id, name, command, required(bool), repeatable(bool), description, artifact:{glob, pattern, min_count(default 1), note, any_of:[{glob,pattern}]}}]} (lines 1-19 document the schema in comments). The 7 phases in next_phase order are concept(5 steps)->systems-design(4)->technical-setup(5)->pre-production(11)->production(9)->polish(5)->release(4). Two consumers were read directly: (a) .claude/scripts/artifact-check.sh is a hand-rolled indentation-walking parser (no PyYAML dependency, by design) that evaluates each step's glob/pattern(POSIX ERE via grep -E)/min_count/any_of against disk and prints ONLY observations (PRESENT/ABSENT/SHORT/PATTERN_MISS/NO_CHECK/UNKNOWN) -- its header explicitly cites 'context-management.md rule 2' (scripts emit observations, never verdicts), the same rule CLAUDE.md restates; (b) .claude/skills/help/SKILL.md Step 1 (line 37) reads the catalog as authoritative, Step 1b Globs installed skills and diffs against catalog `command:` values to surface uncataloged skills, Step 4 shells to `artifact-check.sh --phase [current-phase]` and maps its 5 statuses to Complete/Incomplete/MANUAL/UNKNOWN. .claude/skills/gate-check/SKILL.md runs the identical script scoped to the source phase and layers the required/optional + workflow-tier judgment on top.
* DELIVERABLE 1, INFERENCE on two tracks -- whether the schema supports a firm-setup track and an investment-operations track without code change: NO, not fully, and this is VERIFIED by reading the consumers, not assumed. The YAML SHAPE needs no change (phases: is a flat id-keyed dict; investment-ops phase ids could sit alongside firm-setup phase ids, each with its own next_phase chain). But the STATE-TRACKING code assumes exactly one active phase: /help SKILL.md Step 2 (lines 96-105) hardcodes a single 7-row Concept->...->Release name-to-key lookup table against one scalar project.stage, and /gate-check writes that same scalar. A two-track project needs either two stage scalars or a track dimension in project.yaml, PLUS edits to /help's Step 2 table and /gate-check's stage-write logic -- both are skill-file changes, not YAML-schema changes.
* DELIVERABLE 4 -- Skill Testing Framework's four modes, evidence-based. STATIC (`/skill-test static [name|all]`): reads only .claude/skills/[name]/SKILL.md, runs 7 structural checks, produces COMPLIANT/NON-COMPLIANT. Works even with the whole framework folder deleted (README.md:17). SPEC (`/skill-test spec [name]`): reads catalog.yaml's spec: path, reads the spec file (5 test cases: Happy Path/Failure-Blocked/Mode Variant/Edge Case/Director Gate), verdict PASS/PARTIAL/FAIL. BREAKS without the folder (README.md:19). CATEGORY (`/skill-test category [name|all]`): reads quality-rubric.md, scores 4-5 binary PASS/FAIL/WARN metrics for the matching category, verdict COMPLIANT/WARNINGS/NON-COMPLIANT. BREAKS without the folder. AUDIT (`/skill-test audit`): enumerates all skills/agents, cross-checks catalog.yaml's spec: field, produces a coverage table, verdict COMPLETE. DEGRADES without the folder (README.md:18, 'reports that no catalog exists').

* DELIVERABLE 4 -- proposed AAA acceptance bar for new hedge-fund skills/agents: (1) floor = static mode 0-FAIL (U1) plus skill-authoring.md's five obligations, most load-bearing being obligation 1 (a could-not-assess value that outranks pass) and obligation 3 (a skipped step announces itself in the output); (2) control-function agents (CCO/CRO-equivalent) must satisfy D1+D4 plus a strengthened D3 that routes an unresolved compliance escalation outside the investment chain entirely (to the board/external compliance officer) rather than to the CIO -- a genuinely NEW criterion, not a reuse; (3) compliance/risk monitoring skills must satisfy AN1+AN3 as a hard BLOCKING gate, not the ADVISORY default T1/T2 analysis skills get, since a compliance check that can silently skip is the SEC Two Sigma failure mode; (4) any skill recording an investment decision/trade/model change must satisfy P3+P5 and RD3's BLOCKED-requires-external-action distinction; (5) all must pass a real failing-gate test per skill-authoring.md's closing rule ('break the thing it guards, confirm it fails, restore') before being marked AAA-compliant -- a process requirement to write into the HF framework's own audit checklist.
* T2-COMPARISON, most consequential divergence: T2's own verdicts (mapping.txt) treat ADR-related templates and gameplay-code.md as D across the board, with the calibration note stating T2 does not write ADRs. For a hedge fund with a quant/code archetype this is backwards: ADRs and 'never hardcode, always externally configured' are directly what the SEC Two Sigma model-governance failure (context point 3) demands. A T2-style verdict pass taken uncritically would strip exactly the components a hedge fund's control functions rely on most. HF is not simply 'T2 but regulated' -- on the code/model-governance axis it is closer to T1, even though on the domain-content axis it is much closer to T2's near-total D-and-R pattern. This report's component verdicts reflect that split explicitly rather than defaulting to either prior verdict set.
